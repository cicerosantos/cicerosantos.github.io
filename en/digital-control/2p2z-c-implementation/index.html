The 2p2z in C, in the interrupt

The buck's complete interrupt: read the ADC, compute the error, run the 2p2z difference equation, saturate and write the CCR, in float and in fixed point, with the cycle budget and how to measure it.

First, see: Q15 fixed point, Anti-windup and duty saturation

This note puts together everything the trail has built. The 2p2z compensator becomes the difference equation below, the saturation of Anti-windup and duty saturation sits at the output, and the arithmetic is that of Q15 fixed point:

The sequence in each period

  1. The timer reaches the end of the period and generates the update event. That event triggers the ADC.
  2. The ADC finishes the conversion and calls the interrupt.
  3. The interrupt computes the error and the new duty, and saturates it.
  4. It writes the CCR. With preload on, the new value only takes effect in the next period.

Step 4 is what scenario.cpp imitates with s->duty = s->pending: the duty computed from period kkk's sample governs period k+1k+1k+1. With trailing-edge PWM, the edge that matters comes D TsD\,T_sDTs​ into that period, and the total delay is (1+D) Ts(1 + D)\,T_s(1+D)Ts​, the subject of Computation and PWM delay.

Float variant (Cortex-M4F, M33)

This is scenario.cpp's logic, with the error in volts and the coefficients of the buck's default design. That firmware stores the pole p=a2p = a_2p=a2​ as the controller's fourth value and computes with it, and this variant also stores only a2a_2a2​:

#include "stm32g4xx.h"          /* or your MCU's CMSIS header */

#define PWM_N   850u            /* 170 MHz / 200 kHz; ARR = 849 */
#define LSB     (20.0f / 4095.0f)
#define DMIN    0.0f
#define DMAX    0.9f

static const float b0 = 0.23114164f, b1 = -0.43413087f, b2 = 0.20384645f;
static const float a2 = 0.15183580f;             /* = p; a1 = -(1 + a2) = -1.15183580 */
static float u1 = 0.375f, u2 = 0.375f, e1, e2;   /* start at the steady-state duty */
static volatile float vref = 9.0f;

void ADC1_2_IRQHandler(void)
{
    GPIOB->BSRR = GPIO_BSRR_BS0;                   /* measurement pin: high */
    float e = vref - (float)ADC1->DR * LSB;        /* reading DR clears the end-of-conversion flag */
    float u = u1 + a2 * (u1 - u2) + b0 * e + b1 * e1 + b2 * e2;
    if (u < DMIN) u = DMIN;                        /* store the saturated value: anti-windup */
    if (u > DMAX) u = DMAX;
    u2 = u1; u1 = u;
    e2 = e1; e1 = e;
    TIM1->CCR1 = (uint32_t)(u * PWM_N + 0.5f);     /* preload: takes effect next period */
    GPIOB->BSRR = GPIO_BSRR_BR0;                   /* measurement pin: low */
}

u1 + a2*(u1 - u2) is the same as -a1*u1 - a2*u2, because a1=−(1+a2)a_1 = -(1 + a_2)a1​=−(1+a2​): it is the velocity form, which computes the increment Δu\Delta uΔu and adds it to u1. Written this way, it does without a1=−1.15a_1 = -1.15a1​=−1.15, which does not fit in Q15 in the fixed-point variant, and the integrator stays exactly at z=1z = 1z=1. The reference can also get the slew of Anti-windup and duty saturation, by adding a limited step to vref in each interrupt.

Fixed-point variant (Cortex-M0+)

The error stays in ADC codes, the duty in timer counts with 13 fraction bits, and the coefficients in Q2.13, in counts per code, as in the table of Q15 fixed point:

#define FRAC      13
#define REF_CODE  1843                                    /* 9 V * 4095 / 20 V = 1842.75 */
static const int32_t b0q = 7861, b1q = -14764, b2q = 6932;   /* Q2.13 */
static const int32_t a2q = 4975;                             /* a2 = p in Q15; a1 = -(1 + a2) */
static const int32_t UMAX = 765 << FRAC;                     /* 0.9 * 850 counts */
static int32_t uq1 = 319 << FRAC, uq2 = 319 << FRAC;         /* 0.375 * 850 */
static int32_t eq1, eq2;

void ADC1_IRQHandler(void)
{
    int32_t e = REF_CODE - (int32_t)ADC1->DR;              /* error in codes: can be 0 */
    int64_t acc = (int64_t)uq1
                + (((int64_t)a2q * (uq1 - uq2) + (1 << 14)) >> 15)
                + (int64_t)b0q * e + (int64_t)b1q * eq1 + (int64_t)b2q * eq2;
    if (acc < 0) acc = 0;                                  /* saturate in Q13 counts */
    if (acc > UMAX) acc = UMAX;
    uq2 = uq1; uq1 = (int32_t)acc;
    eq2 = eq1; eq1 = e;
    TIM1->CCR1 = (uint32_t)((acc + (1 << (FRAC - 1))) >> FRAC);
}

The states keep the 13 fraction bits. Without them, the integrator's steps, thousandths of a count, would round to zero, as DPWM resolution and limit cycles warns.

The timing budget

At 170 MHz, a 5 µs period has 850 cycles. Out of that time come the ADC conversion, which starts at the beginning of the period, the interrupt entry (12 cycles on the Cortex-M4 with no wait states, according to the manual) and the computation itself. The CCR must be written before the end of the period. The 2p2z equation, as written above, has four multiplications and five additions or subtractions; with the ADC and CCR scaling, about ten operations, typically a few tens of cycles with the FPU. Even with the peripheral accesses, the interrupt uses a small fraction of the period. But don't trust estimates: measure.

  • GPIO pin: the pair of BSRR writes above makes a pulse whose width is the interrupt's duration. On the scope, next to the PWM, you also see the latency from the start of the period and the variation from one period to the next.
  • Cycle counter: on the Cortex-M3, M4 and M7, the DWT counts clock cycles. The M0 and M0+ lack that counter; use the pin there.
CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;     /* once, at initialization */
DWT->CYCCNT = 0;
DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;

uint32_t t0 = DWT->CYCCNT;                          /* at the start of the interrupt */
/* ... */
uint32_t dt = DWT->CYCCNT - t0;                     /* at the end; unsigned subtraction survives wraparound */
if (dt > worst) worst = dt;                         /* keep the worst case, not the average */

Preload off

Without preload (the OC1PE bit on the STM32), the new CCR takes effect at once. If it is written below the counter's current value, that period's compare has already passed, and the pulse may come out doubled or not at all. Turn preload on and accept the period of delay, which the design of Computation and PWM delay already includes.

Fast code

On the STM32G4, run the interrupt from CCM SRAM, without flash wait states. Declare the routine's state static, and don't call library functions inside it.

In the converters

Buck. At 200 kHz, the budget is 850 cycles at 170 MHz, the same number as the timer's counts, because the timer counts at the core clock. The integer reference 1843 regulates at 1843×20/4095=9.00121843 \times 20/4095 = 9.00121843×20/4095=9.0012 V.

Boost and buck-boost. At 100 kHz, the period has 1700 cycles, twice the slack. The boost measures up to 60 V, and the coefficients in counts per code change scale: NPWM q=1700×60/4095=24.9N_{\mathrm{PWM}}\,q = 1700 \times 60/4095 = 24.9NPWM​q=1700×60/4095=24.9.

Exercise 1

An STM32G0 (Cortex-M0+, 64 MHz, no FPU) controls the buck at 200 kHz. How many cycles are there per period? Why is the float variant risky?

Answer

64 MHz×5 µs=32064\ \text{MHz} \times 5\ \text{µs} = 32064 MHz×5 µs=320 cycles. The routine's ten or so float operations become library calls of, typically, tens of cycles each, and they alone can exceed 320. In fixed point they are a few integer multiplications. The M0+ has no 64-bit instruction, but the compiler emulates the few the variant uses.

Exercise 2

The float variant's interrupt computes u=0.3753u = 0.3753u=0.3753. What value goes to the CCR, and what duty is applied? In which period does it take effect?

Answer

0.3753×850+0.5=319.50.3753 \times 850 + 0.5 = 319.50.3753×850+0.5=319.5, truncated to 319: the duty applied is 319/850=0.3753319/850 = 0.3753319/850=0.3753. With preload, it takes effect in the period after the sample's.
