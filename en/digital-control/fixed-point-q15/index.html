Q15 fixed point

The scale of the buck's 2p2z coefficients in fixed point: Qmmm.nnn formats, Q15 multiplication with rounding and saturation, and the coefficients in counts per code in Q3.12.

First, see: Floating point or fixed point, The 2p2z compensator

The 2p2z compensator has coefficients such as 0.23114 and −0.43413. In fixed point (fixed-point), each number becomes an integer with an implicit scale, and this note shows how that scale works. If the core has an FPU and measurement does not ask otherwise, the decision to use fixed point is in Floating point or fixed point.

The Qmmm.nnn format

Qmmm.nnn format

A signed integer XXX represents x=X/2nx = X/2^nx=X/2n: nnn fraction bits and mmm integer bits beyond the sign, in 1+m+n1 + m + n1+m+n bits in total. Q15 (or Q0.15) is the int16_t read as a fraction, from −1 to 1−2−151 - 2^{-15}1−2−15, in steps of 3.05×10−53.05\times10^{-5}3.05×10−5.

Q2.13 covers −4 to 4 in steps of 1.22×10−41.22\times10^{-4}1.22×10−4: it trades resolution for headroom. The product of two Q15 numbers has 30 fraction bits and fits in 32 bits. To return to Q15, add half a step (2142^{14}214) and shift 15 bits:

#include <stdint.h>

static inline int16_t sat16(int32_t x)          /* saturate instead of wrapping */
{
    return x > INT16_MAX ? INT16_MAX : x < INT16_MIN ? INT16_MIN : (int16_t)x;
}

static inline int16_t q15_mul(int16_t a, int16_t b)
{
    int32_t p = (int32_t)a * b;      /* Q30: the cast comes before the multiplication */
    p += 1 << 14;                    /* round instead of truncating */
    return sat16(p >> 15);           /* -1 * -1 = +1 does not fit in Q15: saturate */
}

Three pitfalls

  • Overflow: without saturation, 0.9+0.20.9 + 0.20.9+0.2 in Q15 becomes −0.9-0.9−0.9. A duty cycle that jumps from 0.9 to −0.9 is the worst possible error. On Cortex-M3, M4 and M7, the CMSIS provides __SSAT(x, 16), which saturates in one instruction.
  • Truncation: p >> 15 without the half step always rounds down, a bias that the integrator accumulates.
  • Shifting negatives: in C99, >> of a negative number is implementation-defined. On GCC for ARM it is arithmetic; check your compiler.

To add several products, use a 64-bit accumulator. Each Q15 × Q15 product already takes 31 bits, and two of them added together can overflow 32 bits. On the Cortex-M4 and M7, the SMLAL instruction multiplies and accumulates into 64 bits. On the M4 it takes one cycle (Cortex-M4 TRM, table 3-1); the M7 issues one such operation, 32 × 32 + 64 → 64 bits, per cycle, with a two-cycle result latency (Cortex-M7 TRM, section 1.2.1). The M0 has no such instruction, and the compiler emulates the operation in several.

The buck's 2p2z coefficients

The standard design (crossover at 8 kHz, double zeros at 2 kHz, pole at 60 kHz) has, in duty cycle per volt of error, b0=0.23114b_0 = 0.23114b0​=0.23114, b1=−0.43413b_1 = -0.43413b1​=−0.43413, b2=0.20385b_2 = 0.20385b2​=0.20385 and, in the denominator, a1=−(1+p)=−1.15184a_1 = -(1 + p) = -1.15184a1​=−(1+p)=−1.15184 and a2=p=0.15184a_2 = p = 0.15184a2​=p=0.15184. The aia_iai​ tie uuu to uuu and do not depend on units. In the difference equation, a1a_1a1​ exceeds 1 in magnitude and does not fit Q15. There are two options:

  • Velocity form: rewrite the equation as u[k−1]+a2 (u[k−1]−u[k−2])+…u[k-1] + a_2\,(u[k-1] - u[k-2]) + \dotsu[k−1]+a2​(u[k−1]−u[k−2])+…, so that only a2a_2a2​ must be stored, in Q15: 4975. The a1a_1a1​ is implicit, −(215+4975)/215-(2^{15} + 4975)/2^{15}−(215+4975)/215, and exact.
  • Format with headroom for both: in Q1.14, which runs from −2 to almost 2, a1a_1a1​ = −18872 and a2a_2a2​ = 2488.

In both cases, a1a_1a1​ and a2a_2a2​ share the same format. Because 2n2^n2n is an integer, rounding both with the same scale keeps 1+a1+a2=01 + a_1 + a_2 = 01+a1​+a2​=0 exact, and the integrator stays at z=1z = 1z=1. With a1a_1a1​ in Q1.14 and a2a_2a2​ in Q15, the sum would be −3.05×10−5-3.05\times10^{-5}−3.05×10−5, and the integrator would move to z=1.000036z = 1.000036z=1.000036, outside the unit circle.

Units matter too. The firmware receives ADC codes and writes HRTIM counts. Multiplying the coefficients by NPWM q=2000×4.884 mV=9.77N_{\mathrm{PWM}}\,q = 2000 \times 4.884\ \text{mV} = 9.77NPWM​q=2000×4.884 mV=9.77 gives values in counts per code: 2.2582.2582.258, −4.241-4.241−4.241 and 1.9911.9911.991. Now all three exceed 1 in magnitude, and the format needs headroom: ∣b1∣=4.24|b_1| = 4.24∣b1​∣=4.24 does not fit Q2.13 (±4), but fits Q3.12 (±8). The equation's states also keep the 12 fraction bits: without them, the integrator's steps, hundredths of a count, would round to zero, as DPWM resolution and limit cycles warns. The script below quantizes the coefficients and measures the effect:

import numpy as np
fs, q, N = 200e3, 20/4095, 2000             # 400 MHz / 200 kHz: counts per period
b = np.array([0.23114164, -0.43413087, 0.20384645]); p = 0.15183580
a1, a2 = -(1 + p), p                       # denominator 1 + a1 z^-1 + a2 z^-2
K = N * q                                  # from duty cycle/volt to counts/code
ki = b.sum() / (1 - a2)                    # integrator step per sample
for n in (15, 14):                         # a1 and a2 on the same scale: 1 + a1 + a2 = 0 exactly
    A1, A2 = round(a1 * 2**n), round(a2 * 2**n)
    print(f"a in Q{15 - n}.{n}", A1, A2, 2**n + A1 + A2)   # Q0.15: -37743 does not fit int16
for name, n, scale in [("Q15 d/V", 15, 1), ("Q2.13 d/V", 13, 1), ("Q4.11 d/V", 11, 1),
                       ("Q3.12 cnt/code", 12, K), ("Q4.11 cnt/code", 11, K)]:
    B = np.round(b * scale * 2**n)         # the integers written to the firmware
    bq = B / 2**n / scale
    a2q = np.round(a2 * 2**15) / 2**15     # a2 in Q15: 4975; a1 = -(1 + a2) implicit
    f = np.abs(np.log(np.roots(bq))) * fs / (2 * np.pi)
    print(name, B.astype(int), np.round(f), f"{100 * (bq.sum() / (1 - a2q) / ki - 1):+.1f} %")

The table has two lessons:

  • The margin barely changes. Near the crossover, an error of 10−410^{-4}10−4 in a coefficient of 0.4 is negligible.
  • The integrator and the double zero change a lot. The integral gain is proportional to b0+b1+b2=8.6×10−4b_0 + b_1 + b_2 = 8.6\times10^{-4}b0​+b1​+b2​=8.6×10−4, a sum of nearly equal numbers that cancel. A double zero is ill-conditioned: an error δ\deltaδ in the coefficients separates it by about δ\sqrt{\delta}δ​. That is why the scale matters: the integral-gain error falls from 13.9 % in Q2.13 per volt to 2.0 % in Q3.12 per code.

In the converters

Buck. In Q3.12, the coefficients in counts per code stay within 2.0 % of the exact integral gain and keep the 41.3° margin; the code is in Floating point or fixed point. The aggressive design, with b1=−15.4b_1 = -15.4b1​=−15.4 counts per code, needs Q4.11 (±16); the unstable one, with −21.2, does not fit even there. Changing the design may need another format: the code must check the range before writing.

Boost. The standard 2p2z has b0=0.165b_0 = 0.165b0​=0.165, b1=−0.319b_1 = -0.319b1​=−0.319 and b2=0.155b_2 = 0.155b2​=0.155 per volt: again, a small sum next to each term.
