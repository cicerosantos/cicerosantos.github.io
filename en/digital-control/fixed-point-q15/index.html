Q15 fixed point

Without an FPU, coefficients and signals become scaled integers: Qm.n formats, Q15 multiplication with rounding and saturation, and the scaling of the buck's 2p2z coefficients.

First, see: The 2p2z compensator

The 2p2z compensator has coefficients such as 0.23114 and −0.43413. With a floating-point unit, they go into the code as they are. Without one, each number becomes an integer with an implicit scale.

Float or fixed point?

  • With an FPU (Cortex-M4F, M7, M33 with FPU, such as the STM32G4, F4 and H7): use float. The single-precision FPU multiplies and adds in one to three cycles (typical datasheet figures, not measured here), and the 24-bit mantissa is more than enough for this loop.
  • Without an FPU (Cortex-M0 and M0+, such as the STM32G0 and C0): every float operation becomes a library call of, typically, tens of cycles. With a 5 µs period and a 64 MHz core, there are only 320 cycles per period. Here fixed point is used.

Hidden double precision

On a single-precision FPU, 0.5 is a double, and x * 0.5 is computed in software. Write 0.5f, and compile with -Wdouble-promotion so the compiler points out the cases.

The Qm.n format

Q2.13 covers −4 to 4 in steps of 1.22×10−41.22\times10^{-4}1.22×10−4: it trades resolution for headroom. The product of two Q15 numbers has 30 fraction bits and fits in 32 bits. To return to Q15, add half a step (2142^{14}214) and shift by 15 bits:

#include <stdint.h>

static inline int16_t sat16(int32_t x)          /* saturate instead of wrapping */
{
    return x > INT16_MAX ? INT16_MAX : x < INT16_MIN ? INT16_MIN : (int16_t)x;
}

static inline int16_t q15_mul(int16_t a, int16_t b)
{
    int32_t p = (int32_t)a * b;      /* Q30: the cast comes before the multiplication */
    p += 1 << 14;                    /* round instead of truncating */
    return sat16(p >> 15);           /* -1 * -1 = +1 doesn't fit in Q15: saturate */
}

Three pitfalls

  • Overflow: without saturation, 0.9+0.20.9 + 0.20.9+0.2 in Q15 becomes −0.9-0.9−0.9. A duty that jumps from 0.9 to −0.9 is the worst possible error. On the Cortex-M3 and M4, CMSIS offers __SSAT(x, 16), which saturates in one instruction.
  • Truncation: p >> 15 without the half step always rounds down, a bias that the integrator accumulates.
  • Shifting negatives: in C99, >> of a negative number is implementation-defined. In GCC for ARM it is arithmetic; check your compiler.

To add several products, use a 64-bit accumulator. Each Q15 × Q15 product already takes 31 bits, and two of them added can overflow 32 bits. On the Cortex-M4, the SMLAL instruction multiplies and accumulates in 64 bits in one cycle, according to the core's manual. The M0 has no such instruction, and the compiler emulates the operation with several.

The buck's 2p2z coefficients

The default design (crossover at 8 kHz, double zeros at 2 kHz, pole at 60 kHz) has, in duty per volt of error, b0=0.23114b_0 = 0.23114b0​=0.23114, b1=−0.43413b_1 = -0.43413b1​=−0.43413, b2=0.20385b_2 = 0.20385b2​=0.20385 and, in the denominator, a1=−(1+p)=−1.15184a_1 = -(1 + p) = -1.15184a1​=−(1+p)=−1.15184 and a2=p=0.15184a_2 = p = 0.15184a2​=p=0.15184. The aia_iai​ relate uuu to uuu and don't depend on the units. In the difference equation, a1a_1a1​ exceeds 1 in magnitude and doesn't fit in Q15. There are two ways out:

  • Velocity form: rewrite the equation as u[k−1]+a2 (u[k−1]−u[k−2])+…u[k-1] + a_2\,(u[k-1] - u[k-2]) + \dotsu[k−1]+a2​(u[k−1]−u[k−2])+…, so that only a2a_2a2​ has to be stored, in Q15: 4975. a1a_1a1​ stays implicit, −(215+4975)/215-(2^{15} + 4975)/2^{15}−(215+4975)/215, and exact.
  • A format with headroom for both: in Q1.14, which goes from −2 to almost 2, a1a_1a1​ = −18872 and a2a_2a2​ = 2488.

Either way, a1a_1a1​ and a2a_2a2​ share one format. Since 2n2^n2n is an integer, rounding both at the same scale keeps 1+a1+a2=01 + a_1 + a_2 = 01+a1​+a2​=0 exact, and the integrator stays at z=1z = 1z=1. With a1a_1a1​ in Q1.14 and a2a_2a2​ in Q15, the sum would be −3.05×10−5-3.05\times10^{-5}−3.05×10−5, and the integrator would move to z=1.000036z = 1.000036z=1.000036, outside the unit circle.

Units matter too. The firmware receives ADC codes and writes counts to the CCR. Multiplying the coefficients by NPWM q=850×4.884 mV=4.15N_{\mathrm{PWM}}\,q = 850 \times 4.884\ \text{mV} = 4.15NPWM​q=850×4.884 mV=4.15, they become counts per code: 0.9600.9600.960, −1.802-1.802−1.802 and 0.8460.8460.846. Now b1b_1b1​ exceeds 1, and the format needs headroom: Q1.14 is enough, and Q2.13 accepts larger designs. The script below quantizes the coefficients and measures the effect:

import numpy as np
fs, q, N = 200e3, 20/4095, 850
b = np.array([0.23114164, -0.43413087, 0.20384645]); p = 0.15183580
a1, a2 = -(1 + p), p                       # denominator 1 + a1 z^-1 + a2 z^-2
K = N * q                                  # from duty/volt to counts/code
ki = b.sum() / (1 - a2)                    # integrator step per sample
for n in (15, 14):                         # a1 and a2 at the same scale: 1 + a1 + a2 = 0 exactly
    A1, A2 = round(a1 * 2**n), round(a2 * 2**n)
    print(f"a in Q{15 - n}.{n}", A1, A2, 2**n + A1 + A2)   # Q0.15: -37743 does not fit in int16
for name, n, scale in [("Q15 d/V", 15, 1), ("Q2.13 d/V", 13, 1), ("Q4.11 d/V", 11, 1),
                       ("Q2.13 cnt/code", 13, K), ("Q1.14 cnt/code", 14, K)]:
    B = np.round(b * scale * 2**n)         # the integers stored in the firmware
    bq = B / 2**n / scale
    a2q = np.round(a2 * 2**15) / 2**15     # a2 in Q15: 4975; a1 = -(1 + a2) implicit
    f = np.abs(np.log(np.roots(bq))) * fs / (2 * np.pi)
    print(name, B.astype(int), np.round(f), f"{100 * (bq.sum() / (1 - a2q) / ki - 1):+.1f} %")

The table has two lessons:

  • The margin barely changes. Near the crossover, an error of 10−410^{-4}10−4 in a coefficient of 0.4 is negligible.
  • The integrator and the double zero change a lot. The integral gain is proportional to b0+b1+b2=8.6×10−4b_0 + b_1 + b_2 = 8.6\times10^{-4}b0​+b1​+b2​=8.6×10−4, a sum 270 times smaller than b0b_0b0​, made of nearly equal numbers that cancel. A double zero is ill-conditioned: an error δ\deltaδ in the coefficients splits it by about δ\sqrt{\delta}δ​. That is why scaling matters: in Q2.13, the coefficients in counts per code use four times more of the range than in duty per volt, and the integral gain's error falls from 13.9 % to 0.5 %.

In the converters

Buck. The coefficients in counts per code, in Q2.13, stay within 0.5 % of the exact integral gain and keep the 41.3° margin. This is the fixed-point variant of The 2p2z in C, in the interrupt. Q2.13 covers up to ±4, but the buck's aggressive design reaches b1=−6.56b_1 = -6.56b1​=−6.56 counts per code, and the unstable one −8.99. Changing designs may call for another format, and the code should check the coefficients' range before storing them.

Boost. The default 2p2z has b0=0.165b_0 = 0.165b0​=0.165, b1=−0.319b_1 = -0.319b1​=−0.319 and b2=0.155b_2 = 0.155b2​=0.155 in duty per volt: again, a small sum compared with each term.
